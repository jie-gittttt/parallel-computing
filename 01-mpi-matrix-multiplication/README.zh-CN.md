# MPI 矩阵乘法 —— D = A×B + C

[English](README.md) | [中文](README.zh-CN.md)

用 MPI 实现的分布式矩阵计算。最终决定性的提速来自为缓存局部性重排循环，而不是来自增加进程数。

## 1. 概述

任务是用**纯消息传递**计算 `D = A×B + C`，三个矩阵均为 1023×1023 的双精度矩阵——不用共享内存，
不用线程，不用 BLAS。进程 0 负责读入输入、分发数据、收集结果并写回。

作业有两个目标，第二个才是真正有意思的部分：

1. **任务划分。** 用 MPI 集合通信把一个稠密线性代数核切分到多个进程上，并处理一个不能整除的矩阵维度。
2. **访存行为。** 量化有多少加速来自*内层循环怎么走内存*，而不是来自有多少个核在跑。

这是标准的 BLAS-3 计算核，因此循环顺序这一课可以直接迁移到任何稠密线性代数和模板计算（stencil）代码上。

## 2. 核心贡献

- **主-从模式 + 按行分块划分** —— 进程 0 负责 I/O 与调度，其余进程只做计算。
- **全程使用变长集合通信。** 1023 既不能被 2 也不能被 4 整除，因此 A 和 C 都用 `MPI_Scatterv`
  分发、D 用 `MPI_Gatherv` 收集，`displs` 由累计行偏移算出；B 用 `MPI_Bcast` 整体广播。
- **两项串行优化各自独立实现并单独计时** —— i-k-j 循环交换，以及预先转置 B ——
  这样才能把它们的贡献与并行的贡献分开衡量。
- **每次运行都做正确性校验**，通过助教提供的 `verify_` 校验程序（输出 `比对成功！`）。
- **保留原始计时日志**，包括课程共享服务器上三次不同会话的记录，其中有些不那么好看的数字也一并保留。

## 3. 方法与架构

### 数据分发

| 矩阵 | 形状 | 方法 | 原因 |
| :--- | :--- | :--- | :--- |
| **A** | M×N，按行切 | `MPI_Scatterv` | 1023 不能被 2 或 4 整除，必须做不均匀分发 |
| **C** | M×K，按行切 | `MPI_Scatterv` | 同上，且要与 A 的行块对齐 |
| **B** | N×K，全量 | `MPI_Bcast` | 计算 D 的**任意一行**都需要完整的 B，无法切分 |
| **D** | M×K，收集 | `MPI_Gatherv` | 与 Scatterv 对称，把大小不一的各个行块拼回完整矩阵 |

```
                    ┌─────────────┐
   进程 0  ────────▶│   读入输入   │  RandMatrix.txt  (A, B, C)
   （主进程）        └──────┬──────┘
                           │  Scatterv A（按行）  sendcounts = {256,256,256,255} × 1023
                           │  Scatterv C（按行）
                           │  Bcast    B（全量，1023×1023 ≈ 8.4 MB）
                           ▼
        ┌──────────┬──────────┬──────────┬──────────┐
        │  P0      │  P1      │  P2      │  P3      │  局部 D_block += A_block × B
        └────┬─────┴────┬─────┴────┬─────┴────┬─────┘
             └──────────┴────┬─────┴──────────┘
                             │  Gatherv D
                             ▼
                    ┌─────────────┐
                    │   写出结果   │  result.txt
                    └─────────────┘
```

**为什么按行划分而不是按列？** 矩阵以行优先方式存储，一个行块就是一段连续内存，
可以直接交给集合通信；按列切分则需要先跨步打包，代价高于它省下的通信量。

### 串行优化一 —— i-k-j 循环交换

最朴素的三重循环是 i-j-k：

```cpp
for (int i = 0; i < M; ++i)
    for (int j = 0; j < K; ++j)
        for (int k = 0; k < N; ++k)
            D[i][j] += A[i][k] * B[k][j];   // B[k][j] 步长为 K
```

内层下标是 `k`，所以 `B[k][j]` 每次迭代跳一整行（K 个元素）。一个 64 字节的 cache line
在被换出前只用到 8 字节——**有效缓存利用率约为 1/8**。

交换为 i-k-j：

```cpp
for (int i = 0; i < M; ++i)
    for (int k = 0; k < N; ++k)
        for (int j = 0; j < K; ++j)
            D[i][j] += A[i][k] * B[k][j];   // 步长均为 1
```

此时 `B[k][j]` 与 `D[i][j]` 都是连续递增的，而 `A[i][k]` 对内层循环是不变量，
编译器可以把它提到寄存器里。每个 cache line 都被用满。
这不是简单地交换 `for` 的顺序——`A[i][k]` 变成循环不变量会改变计算逻辑，累加器也要相应处理。

### 串行优化二 —— 预先转置 B

```cpp
// 先转置一次：Bt 为 K×N，于是 Bt[j][k] 是行连续的
for (int i = 0; i < M; ++i)
    for (int j = 0; j < K; ++j) {
        double s = 0;
        for (int k = 0; k < N; ++k)
            s += A[i][k] * Bt[j][k];        // 两个操作数都连续
        D[i][j] = s + C[i][j];
    }
```

转置的代价是 O(N·K) 次额外搬运，但相对于 1023³ ≈ 10.7 亿次乘加的主循环，这点开销可以忽略。

## 4. 实验与结果

课程共享服务器，1023×1023，用 `MPI_Wtime` 测量计算阶段：

| 进程数 | 朴素 i-j-k | 循环交换后 | 加速比（优化后） |
| :-: | --: | --: | --: |
| 1 | 10.494 s | 7.710 s | 1.00× |
| 2 | 6.659 s | 3.946 s | 1.95× |
| 4 | 3.398 s | **1.225 s** | **6.29×** |

- **纯串行优化：1.36×**（10.494 s → 7.710 s），没有增加任何硬件，完全来自访存改善。
- **4 进程加速比：3.09× → 6.29×**。
- **端到端：10.494 s → 1.225 s，合计 8.57×。**

每次都跑助教提供的校验程序：

```
$ ./verify_ RandMatrix.txt result.txt
比对成功！
```

### 4 进程加速比为什么超过 4？

6.29× 相对 4 个进程是**超线性**的。最合理的解释是缓存：串行时 1023×1023 的 double 矩阵
（约 8.4 MB）放不进 L2，而 4 进程各自只处理 256 行，**每核的工作集被切小**到足以常驻缓存。
再叠加循环交换带来的局部性改善，两个效应复利式地超过了线性。

这是从计时数据推出的解释，不是用硬件计数器测出来的——局限见第 7 节。

### 计时波动

同一份代码在不同会话中的绝对耗时并不一致。三次有记录的会话：

| | 1 进程 | 2 进程 | 4 进程 |
| :--- | --: | --: | --: |
| 会话 A | 7.640 s | 3.836 s | 2.762 s |
| 会话 B | 5.400 s | 4.135 s | 3.033 s |
| 会话 C（上表所用） | 10.494 s | 6.659 s | 3.398 s（优化前） |

服务器与别人的作业共享，CPU 频率与缓存争用都会变化。上表取的是**最后一次带完整校验记录**的运行；
各会话的原始输出在 [`results/run-log.txt`](results/run-log.txt) 与
[`results/timing-sessions.txt`](results/timing-sessions.txt) 中可查。

## 5. 技术栈

- **语言**：C++11
- **并行**：MPI（`mpic++`，课程服务器上的 MPICH / OpenMPI）
- **计时**：`MPI_Wtime`
- **构建**：单编译单元，不需要构建系统

## 6. 安装与运行

**环境要求** —— 一个 MPI 实现（`mpic++` 在 `PATH` 上），以及一个 1023×1023 的
`RandMatrix.txt`（含 A、B、C 三个矩阵），格式见 [`report/io-spec.pdf`](report/io-spec.pdf)。

```bash
mpic++ -o Matrix src/Matrix.cpp -std=c++11
mpirun -np 4 ./Matrix        # 读 RandMatrix.txt，输出 result.txt
```

进程数是运行参数；`sendcounts` 和 `displs` 会按进程数重新计算，所以 `-np 2`、`-np 8` 都能跑。

**预期输出** —— 各进程的计时行，末尾是总时间：

```
------------------------------------------
Job Complete.
Total execution time with 4 processes: 1.225 seconds
------------------------------------------
```

## 7. 局限性

- **超线性结果在硬件层面没有得到解释。** 缓存工作集的说法与数据一致，但没有用性能计数器验证过。
  严谨的做法是在各进程数下测量 L2/L3 缺失率。
- **扩展性只测到 4 进程。** 没有做强扩展或弱扩展研究，因此通信开销超过计算开销的拐点在哪里是未知的。
- **共享服务器噪声。** 各次运行并未隔离，所以绝对耗时——甚至加速比曲线的形状——都带有负载相关的误差。
  这也是保留原始日志的原因。
- **只测了一个矩阵规模。** 所有结论都是在 N = 1023 下得出的，没有展示矩阵规模完全超出缓存后这个权衡如何变化。
- **B 每次都是整体广播。** 8.4 MB 的广播是主要的通信开销，且不随进程数下降。生产级实现会采用能同时切分 B
  的分解方式（SUMMA、Cannon），或用 `MPI_Isend`/`MPI_Irecv` 把通信与计算重叠起来。
- **只用了阻塞式集合通信。** 没有尝试计算与通信的重叠。
